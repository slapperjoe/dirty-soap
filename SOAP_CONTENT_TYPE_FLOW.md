# Findings: SOAP Content-Type flow in the unified explorer

Task: t_150c4beb (findings for t_da120619, feeds t_95f41b31 implementation)
Verified against branch `wt/t_150c4beb` (commit fafed63), 2026-08-31.

## TL;DR

Two independent defects combine to produce the reported symptom (UI says
`application/soap+xml`, wire says `text/xml`):

1. **Display bug (locked row):** The unified explorer's request editor is
   `MonacoRequestEditorWithToolbar`, which has **no `contentType` prop at all**
   and never forwards one to `HeadersPanel`. `HeadersPanel` therefore always
   falls back to its hardcoded default `application/soap+xml`
   (`packages/request-editor/src/components/HeadersPanel.tsx:86`). The row is
   read-only (🔒 "Managed by toolbar dropdown"), but the toolbar that would
   manage it does not exist in this component — the lock is decorative and the
   displayed value is a constant, unrelated to the request's real
   `contentType`.
2. **Data bug (wrong stored value):** Sample requests created by the Rust
   backend are stamped `contentType: "text/xml"` (hardcoded), and every
   execution path falls back to `text/xml` when a request has no
   `contentType`. So the outgoing wire value genuinely is `text/xml` (or
   `text/xml; charset=utf-8` via the SOAP 1.1 default in `SoapVersion::content_type()`).

The two screens show different things because they read different sources:
- Operation/Project **summary screens** show `req.contentType` (the stored
  `text/xml`) or the sample-derived metadata.
- The **editor's locked header row** shows the `HeadersPanel` fallback
  `application/soap+xml`.

## 2. Current precedence rules (as implemented)

| Stage | Precedence (highest first) |
|---|---|
| Sample creation (load) | hardcoded `"text/xml"` — no override possible (`unified_explorer_commands.rs:238`, `:136`) |
| Sample creation (refresh, new ops) | hardcoded `"text/xml"` (`:136`); existing user requests untouched |
| New request (live, `handleUnifiedNewRequest`) | `sample.contentType` → `operation.input?.contentType` → `"application/soap+xml"` |
| New request (dead cmd, `new_unified_request`) | `op.input?.contentType` → `"application/soap+xml"` |
| Editor display (unified) | constant `"application/soap+xml"` (HeadersPanel fallback; real value never displayed) |
| Editor display (legacy workspace) | `request.contentType` (editable via `RequestTypeSelector` dropdown) |
| Summary screens (unified) | stored `req.contentType` (falls back to displaying `text/xml`) |
| Execution (unified) | `req.contentType` → `"text/xml"` → (backend) SOAP-version default |
| Execution (legacy) | `fixContentType`: SOAP `contentType` field authoritative → header synced; no context → `"application/soap+xml"` |
| Backend send | `content_type` param → `SoapVersion::content_type()` (`text/xml; charset=utf-8` for 1.1) |

There is **no interface/project-level content-type** anywhere:
`UnifiedProject` (`shared/src/models.ts:405`) has `soapVersion` and
`bindingName` but no `contentType`; nothing in the project JSON written by
`parse_wsdl_as_project` (unified_explorer_commands.rs:56-67) carries one.

## 3. Why the user sees what they see

- Sample requests are stamped `text/xml` on load → summaries show `text/xml`
  → execution sends `text/xml`.
- The editor's locked row shows `application/soap+xml` because the component
  never receives the request's content type and falls back to its constant.
  Nothing on that screen reflects the stored value, so it reads as a
  contradiction.
- "New request: header locked, says application/soap+xml, still sent as
  text/xml" — the lock row is the same constant fallback; the created request
  inherited `text/xml` from the sample (1.3), and execution prefers the stored
  value (1.5).

## 4. Minimal change points for an interface-level Content-Type override

Goal (per t_da120619): a content-type set at interface (unified project) level
propagates to sample requests, action/sample execution, and newly created
requests; existing requests are updated across; `text/xml` remains only when
selected or the default.

1. **Model + storage:** add `contentType?: string` to `UnifiedProject`
   (`shared/src/models.ts:405`); persist in the project JSON written by
   `parse_wsdl_as_project` / `refresh_unified_project`
   (`unified_explorer_commands.rs:56-67`, `:171-182`). A Tauri setter command
   (e.g. `set_unified_project_content_type`) that updates the JSON and
   re-stamps requests (item 5) is the write path.
2. **Single resolution helper (backend):** replace the three hardcoded
   literals in `unified_explorer_commands.rs` (lines 136, 238, and the
   fallback logic at 386-390) with
   `resolve_content_type(project)` =
   `project.contentType` → SOAP-version default (`text/xml; charset=utf-8`
   for 1.1 / `application/soap+xml; charset=utf-8` for 1.2, per
   `SoapVersion::content_type()`). `build_operation_json`/
   `refresh_unified_project` need the project's `soapVersion` passed in.
   Update the two test assertions (lines 495, 553).
3. **Sample display + creation:** `generateSampleWithMetadata`
   (`shared/src/utils/soapUtils.ts:316`) — add the project/interface override
   ahead of the `text/xml; charset=utf-8` fallback (the panel receives
   `operation`; either thread `contentType` down from
   `UnifiedExplorerMain`/`SampleRequestPanel` props or keep
   `sampleMetadata.contentType` as the carrier). `UnifiedExplorerMain.tsx:541`
   and the `|| 'text/xml'` fallbacks at `:227`/`:240` should use the same
   resolution so stored, displayed, and sent values agree.
4. **Display fix (independent of the override feature):**
   `MonacoRequestEditorWithToolbar.tsx` — add an optional `contentType` prop
   and forward it to `HeadersPanel` (lines 206-213);
   `UnifiedExplorerMain.tsx:595` passes
   `contentType={editingRequest?.contentType}`. Until then the 🔒 row can
   never be correct in the unified explorer. Also fix
   `handleExecuteRequest` (lines 215/218/224) to forward `op.action`,
   `op.targetNamespace`, and `project.soapVersion` instead of
   null/hardcoded-1.1.
5. **Propagation to existing requests:** when the interface override is
   set, rewrite `contentType` on all descendant requests — sample and user
   requests alike (the user's ask). Simplest correct rule: update every
   request whose current `contentType` is empty or a known default
   (`text/xml`, `text/xml; charset=utf-8`, `application/soap+xml`, the
   charset-suffixed 1.2 form — the list already exists in
   `useRequestExecution.ts:53` `legacyDefaults`); keep explicitly chosen
   non-default values if per-request overrides are to be preserved. Do it in
   one place (the setter command in item 1) so disk + in-memory state +
   summary screens all agree.
6. **Consistency cleanups (same class):** retire or align the dead
   `new_unified_request` command (`unified_explorer_commands.rs:363`,
   `lib.rs:597`) with the live `handleUnifiedNewRequest`
   (`MainContent.tsx:318`), and align `useContextMenu.ts:196` /
   `MainContent.tsx:639` fallbacks to the shared resolver.

## 5. Secondary findings (verified, out of scope for the content-type fix)

- `UnifiedExplorerMain.tsx:224` hardcodes `soapVersion: '1.1'` in
  `execute_soap_request` — a SOAP 1.2 unified project executes as 1.1 (wrong
  SOAPAction header behavior + wrong fallback content type).
- `UnifiedExplorerMain.tsx:215,218` send `action: null` /
  `targetNamespace: null` — the outgoing `SOAPAction` header is always empty
  for unified-explorer requests despite `op.action` being known.
- `unified_explorer_commands.rs:269` builds sample envelopes with
  `SoapVersion::Soap11` regardless of `project.soapVersion`.
- `client.rs:206-267` `execute_raw_with_cancel` does not apply the request's
  custom `headers` (webview sends them at
  `UnifiedExplorerMain.tsx:228`); only Content-Type/SOAPAction go out.
- `handleExecuteRequest` never populates `req.request` before sending —
  it sends `currentXml` and only persists via `persistRequestUpdate(req, currentXml)`
  (line 260); `lastResponse` is attached via mutation on the project object
  (line 253). Not a content-type issue, but relevant when rewiring the
  execution call.
